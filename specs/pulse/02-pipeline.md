# 02 — Конвейер: нормализатор, эпизоды, лестница хранения

> Статус: **draft** · Слой L1/L2

## Нормализатор

Нормализатор превращает наблюдения в выводы. Это **чистая функция над окном
наблюдений** — у неё нет состояния, кроме самого окна, и нет права ходить
куда-либо ещё.

Правила декларативны и читаемы человеком. Это файл, а не модель:

```yaml
inference: home.presence
window: 10m
from:
  - proximity.known_device: {device_alias: [airpods_pro, home_speaker], state: present}
  - network.ssid_class: {value: home}
emit:
  state: user_likely_home
  confidence: weighted        # 1 источник → 0.6, 2+ → 0.86
```

Требования:

- Нормализатор MUST быть детерминированным: одно и то же окно даёт один и тот же
  вывод. Иначе журнал перестаёт быть проверяемым.
- Модель MAY участвовать в нормализации, но только как **предложение правила**,
  которое человек подтверждает и которое затем существует как обычный файл
  правила. Модель MUST NOT быть нормализатором в рантайме. Причина простая:
  вывод, порождённый моделью на лету, невозможно ни воспроизвести, ни отозвать.
- Правило, которое сработало, попадает в журнал по имени.

### Что вывод помнит о своём происхождении

Вывод несёт `derived_from` — список **id сенсоров и имя правила**, но не сами
наблюдения:

```json
{
  "v": 1,
  "inference": "home.presence",
  "t": "2026-08-02T04:09:00+03:00",
  "state": "user_likely_home",
  "confidence": 0.86,
  "derived_from": {"rule": "home.presence@1", "sensors": ["ble.known-devices", "net.ssid-class"]},
  "ttl": "24h"
}
```

Отсюда следует **окно объяснимости**. Пока сырьё живо (минуты), на вопрос
«почему ты так решил» система отвечает конкретными наблюдениями. После истечения
TTL наблюдений остаётся только имя правила и список сенсоров.

Это цена, а не баг. Полная объяснимость задним числом требует хранить сырьё, а
хранить сырьё — ровно то, чего архитектура избегает. Размен назван здесь, чтобы
он не всплыл потом как требование «ну хотя бы неделю сырья, для отладки».

## Episode Builder

Episode Builder решает, стоит ли вообще связывать выводы между собой и оставлять
след. Он запускается **на границах**, а не непрерывно: при устойчивой смене
состояния, при завершении интервала, по расписанию — но не на каждое событие.

Ворота (все MUST выполняться одновременно):

1. **Два независимых источника.** Эпизод из одного сенсора — это шум с
   претензией на смысл.
2. **Минимальная длительность.** Состояние, не прожившее `min_duration`
   (по умолчанию 10 минут), эпизодом не становится.
3. **Бюджет.** См. ниже. Если бюджет исчерпан, builder MUST объединять эпизоды,
   а не дописывать новые.

Формат эпизода:

```json
{
  "v": 1,
  "id": "ep_2026-08-02_0409",
  "start": "2026-08-02T04:09+03:00",
  "end":   "2026-08-02T05:40+03:00",
  "place": "home",
  "facets": ["garden", "music"],
  "note": "рабочий контекст завершён",
  "sources": ["ble.known-devices", "net.ssid-class", "media.now-playing"],
  "confidence": 0.8
}
```

В человекочитаемом виде это одна строка — та самая, ради которой всё
остальное существует:

```
04:09 · дома · сад · музыка · рабочий контекст завершён
```

## Бюджет памяти

Самая надёжная защита здесь — не шифрование и не обещание. Квота.

| Ограничение | Значение по умолчанию |
|---|---|
| эпизодов в сутки | ≤ 24 |
| длина `note` | ≤ 280 символов |
| `facets` на эпизод | ≤ 5 |
| суммарный прирост L3 в сутки | ≤ 8 КБ |

Система, способная записать двадцать четыре строки в день, структурно не может
быть архивом наблюдения. Ей нечем. Это свойство не зависит от добросовестности
кода, от версии модели и от того, что кто-то поменяет в настройках через год —
поэтому оно и стоит в основании, а не рядом с ним.

Превышение бюджета MUST приводить к слиянию эпизодов, а не к расширению квоты.
Настройки, поднимающей потолок, в системе нет.

## Лестница хранения

| Слой | Что | Где | TTL | Переживает перезагрузку | Доступен слою действия |
|---|---|---|---|---|---|
| **L0** | внутреннее состояние сенсора | память процесса | секунды | нет | нет |
| **L1** | наблюдения | ring buffer в RAM | ≤ 60 мин (по манифесту) | **нет** | нет |
| **L2** | выводы | локальная БД | ≤ 24 ч | да | только агрегатами |
| **L3** | эпизоды | локальная БД, шифрование at rest | до удаления пользователем | да | да |

Ключевые требования:

- L1 MUST NOT касаться диска. Ни файла, ни временного файла, ни свопа: своп для
  процесса буфера отключается явно. Это точка, на которой держится честность
  кнопки «Forget the last hour» — забывать нечего искать по диску.
- L3 шифруется ключом, привязанным к разблокировке устройства.
- Опциональный скользящий горизонт L3 (по умолчанию 12 месяцев) — включается
  пользователем, не агентом.

## Удаление

Удаление — операция супервизора, не агента. Модель не является стороной в этом
разговоре ни в одном из сценариев.

**`forget(window)`** — забыть последний интервал:

1. обнулить ring buffer L1 целиком;
2. удалить выводы L2 с `t > now - window`;
3. удалить эпизоды L3, чьё окно пересекается с интервалом;
4. отменить все висящие предложения слоя действия;
5. записать один tombstone.

Требования: операция MUST выполняться менее чем за 1 секунду, MUST работать при
остановленном процессе агента и MUST NOT требовать подтверждения у модели.

**Tombstone** выглядит так и содержит только факт:

```json
{"v": 1, "op": "forget", "window": "1h", "at": "2026-08-02T05:12+03:00"}
```

Он нужен, потому что пропуск, неотличимый от сбоя, — это не контроль, а
надежда. Но tombstone сам по себе — метаданные о поведении, поэтому операция
`forget(all)` удаляет и его.

## Цена

Конвейер теряет информацию на каждой границе, и это невосстановимо. Вывод,
сделанный вчера, нельзя перепроверить по сырью. Эпизод, слитый из-за бюджета,
нельзя разделить обратно. Ошибочное правило нормализатора отравит эпизоды и
будет обнаружено поздно — а исправить задним числом будет уже нечем. Всё это
принимается сознательно: система, которая умеет восстановить прошлое, — это
система, которая его хранила.
